# 05. Клиент модели (llama-server)

## Выбор движка
Ходим в `llama-server` из llama.cpp напрямую. Ollama с мая 2026 (PR ollama#16031 «Remove CGO engines, use llama-server exclusively for GGML models») сама запускает `llama-server` как подпроцесс и пинит его версию файлом `LLAMA_CPP_VERSION`; собственный движок у неё остался только для MLX на Apple Silicon. То есть на нашей платформе Ollama — это менеджер моделей поверх того же бинарника, но без доступа к тому, что нам нужно:

- нет управления MoE-офлоадом (`--n-cpu-moe`), ollama#11772 открыт с августа 2025;
- открытые баги ровно на RDNA4: ollama#16261 (сегфолт при частичном офлоаде на RX 9070), ollama#16624 (регрессия ROCm на gfx1201), ollama#18117 (Vulkan не выделяет ~1 ГБ при >14 ГБ свободных), ollama#18129 (перезапуск раннера с дефолтным ctx 4096);
- нет прямого управления кэшем префикса и слотами, на которых построена схема промпта из `04-translation-pipeline.md`.

Совместимость с Ollama по OpenAI-совместимому API сохраняем как fallback в конфиге: тот же `/v1/chat/completions`, отличия — имя модели и отсутствие `/health` (вместо него `/api/tags`).

## Задачи
- [ ] `reqwest` клиент к `POST {base_url}/v1/chat/completions`, `stream: true`, парсинг SSE-чанков.
- [ ] Настройки: `base_url`, `model`, `temperature`, `top_p`, `top_k`, `min_p`, `repeat_penalty`, `max_tokens`, `timeout`, `api_key` (пусто для локального).
- [ ] Структурированный вывод для компактификации: `response_format: {type: json_schema}` (llama-server поддерживает), фолбэк на «только JSON» в промпте + `serde_json` с очисткой ```json.
- [ ] Health-check: `GET /health` раз в 10 с, статус в `LlmStatus`.
- [ ] Подсчет токенов из `usage` в ответе для метрик.
- [ ] Снятие метрик с `GET /metrics` (сервер запускается с `--metrics`), см. раздел «Метрики».
- [ ] Клиент эмбеддингов: `POST {embed_url}/v1/embeddings`, батчи по 32 абзаца, размерность из конфига. **Нормализация не нужна** — llama-server отдаёт уже нормализованные векторы (проверено: норма 1.0000).

## Параметры сэмплинга
Дефолты llama.cpp (`common/common.h`): `temp 0.80`, `top_k 40`, `top_p 0.95`, `min_p 0.05`, `repeat_penalty 1.00` (выключен). Осторожно: README llama-server в прозе утверждает, что `repeat_penalty` по умолчанию 1.1 — это устаревший текст, в коде 1.0.

Наши значения для перевода:

| Параметр | Значение | Почему |
|---|---|---|
| `temperature` | 0.2-0.3 | Воспроизводимость: иначе кэш переводов бесполезен для сравнения моделей и промптов |
| `top_p` | 0.9 | |
| `top_k` | 64 | |
| `min_p` | 0.05 | |
| `repeat_penalty` | **1.0, явно** | Штраф за повтор прицельно вреден: в художественном тексте обязаны повторяться имена персонажей, глаголы речи и термины глоссария. Мы сами кладём в хвост промпта предыдущие абзацы и RAG-пары с теми же именами, так что штраф работал бы против требования «следуй глоссарию» |

Значения передаются **в каждом запросе**, а не берутся из командной строки сервера: `top_k`, `min_p`, `repeat_penalty` — расширения llama.cpp к OpenAI-схеме, сервер их принимает в теле запроса.

Если карточка модели рекомендует свой профиль сэмплинга (как HauhauCS-сборка Gemma 4: `temp 0.6`, `repeat_penalty 1.1`), он, как правило, подобран под creative writing и roleplay, а не под перевод. Берём оттуда только `top_k`/`top_p`/`min_p`, температуру и штраф за повтор ставим свои. Расхождение проверяется через `eval`.

### Расцензуренные сборки
Для художественного текста safety-тюнинг даёт два режима отказа: громкий (модель отказывается — ловится `validate`) и **тихий (переводит, но смягчает)**. Второй опаснее, потому что проходит все текущие проверки: ответ не пустой, не эхо оригинала, число предложений сходится, служебных фраз нет. Поэтому расцензуренная сборка — обоснованный выбор, но не бесплатный:

- метод абляции обычно не раскрывается и умеет ронять следование инструкциям, а на нём держится глоссарий и JSON-компактификация;
- «0/465 Refusals» — метрика отказов, о качестве перевода не говорит ничего;
- если тюнинг делался на английском материале (`language: en` в метаданных), под FR/ES/IT/DE и русский выход он не проверялся;
- формулировка «reasons before answering» конфликтует с требованием «переводи только данный абзац, без пояснений» и повышает долю ретраев.

Решается замером против немодифицированного контроля, метрики — в `11-core-api-and-cli.md`.

**Итог проверки: расцензуренная сборка не нужна.** Прямое сравнение на полной книге (92 абзаца явной эротики от первого лица, EN→RU, жадное декодирование, один seed, один промпт):

| | `ggml-org/gemma-4-26B-A4B-it` QAT Q4_0 | HauhauCS QAT Uncensored Q4_K_M |
|---|---|---|
| Размер | **14.6 ГБ** | 16.8 ГБ |
| Влезает в VRAM целиком | **да, под ROCm** | нет ни под одним бэкендом |
| **Отказов** | **0** | **0** |
| Отношение длин | 1.10 | 1.09 |
| Лексика регистра | 49 | 47 |
| Сильная обсценная | **2** | 1 |
| Эвфемизмы | 4 | 3 |
| Род 1 л., женский | 79 | 76 |
| Слова вне словаря, реальные ошибки | **0** | 2 («эректа», «сосцы сосчу») |

Базовая модель не отказала ни разу, дала тот же регистр (и даже чуть больше сильной обсценной лексики) и **меньше ошибок**. Плюс она на 2.2 ГБ меньше, а это решает: под ROCm она умещается в VRAM целиком, тогда как расцензуренной офлоад нужен при любом бэкенде (см. раздел «Бэкенд»).

Строки таблицы, кроме размера, получены однократными прогонами. Для качественных признаков (отказы, ошибки, род) это допустимо — они дискретны и не плавают от прогона к прогону. Сравнивать по ним время было бы нельзя, поэтому времени в таблице нет.

Значит «0/465 Refusals» измеряет проблему, которой для нашей задачи нет: базовая Gemma 4 литературную эротику переводит без сопротивления. **По умолчанию берём `ggml-org/gemma-4-26B-A4B-it` Q4_0.**

Существенная оговорка: системный промпт во всех прогонах содержал требование «не смягчай и не облагораживай, физический дискомфорт переводи как дискомфорт». Возможно, работу делает именно оно, и без него базовая модель смягчала бы сильнее. Это не проверено и стоит проверить — но на выводе не сказывается, потому что инструкция у нас есть в любом случае.

Оговорки о границах замера: один текст, один язык, один жанр; кванты разные (Q4_0 против Q4_K_M), хотя разница в пользу более крупного.

**Замерено** ранее на коротком фрагменте того же текста, Gemma 4 26B-A4B QAT Uncensored:

| Что проверяли | Результат |
|---|---|
| Отказ | нет, `finish_reason: stop`, маркеров отказа нет |
| Пропуски | нет, выравнивание 54/54 предложения |
| Род от первого лица | 6 из 6 верно |
| Прямая лексика | сохраняется («оттрахал мне лицо», «дырка», «задница») |
| Регистр | **садится**: русский выход нейтрально-клинический (член, ствол), а не обсценный, при грубом оригинале |
| Физический дискомфорт | **смягчается**: `gag` → «перехватило дыхание» вместо «подступал рвотный позыв» |

Вывод: расцензуривание убрало **отказы**, но не сохранило **регистр**, и смягчение бьёт прицельно по описаниям дискомфорта, а не по сексуальной откровенности. Значит «0/465 Refusals» из карточки модели подтверждается и при этом действительно ничего не говорит о качестве.

Смягчение частично лечится промптом: точечная инструкция («gag = давиться, НЕ «перехватило дыхание»») исправляет конкретное место, а общее требование «передавай обсценную лексику обсценной» базовый словарь почти не сдвигает. Практический вывод для `04-translation-pipeline.md`: регистр и спорные термины закрепляются в `style.register` и `terms` глоссария по конкретной книге, а не разовой фразой в системном промпте.

### Эмбеддинги
`Qwen3-Embedding-0.6B` Q8_0 (639 МБ). Проверено на этой машине:

- **`--pooling last`**, не `cls` — это требование модели, `cls` остался в доках от bge-m3;
- размерность **1024**, совпадает с `[embeddings] dim` из `06-websocket-server.md`; MRL позволяет урезать до 32-1024;
- векторы приходят **уже нормализованными** (норма 1.0000), отдельный шаг не нужен;
- модель instruction-aware: инструкция на стороне запроса даёт +1-5% к качеству поиска, и писать её надо по-английски даже для других языков (рекомендация авторов);
- многоязычность подтверждена: к русскому абзацу его английский эквивалент даёт близость 0.63, немецкий 0.50, французский 0.44 — против 0.23 у неродственного русского абзаца.

**Эмбеддинги считаем на CPU.** Замер:

| Режим | VRAM сверх рабочего стола | Скорость | Книга (92 абзаца) |
|---|---|---|---|
| Vulkan, `-ub 8192 -np 4` | 2.8 ГБ | 23 мс/абзац | 2.1 с |
| Vulkan, `-ub 512 -c 2048 -np 1` | 1.05 ГБ | 23 мс/абзац | 2.1 с |
| **CPU (`-dev none -ngl 0 -t 8`)** | **0** | 110 мс/абзац | **10.1 с** |

Держать второй llama-server в VRAM на этой машине незачем: основная модель занимает 14.71 ГБ из ~15.75 доступных, места под эмбеддинги почти не остаётся, а расчёт всей книги на CPU стоит 10 секунд против 65 секунд перевода. По `backend/ARCHITECTURE.md` воркер эмбеддингов и так низкоприоритетный.

```
llama-server -m models/Qwen/Qwen3-Embedding-0.6B-GGUF/Qwen3-Embedding-0.6B-Q8_0.gguf \
  --embedding --pooling last -ub 512 -c 2048 -np 1 \
  -dev none -ngl 0 -t 8 --host 127.0.0.1 --port 8081
```

## Бэкенд: решает не скорость, а вместимость

**Замерено на полном тексте, оба бэкенда × обе модели × MTP вкл/выкл.** Раскладка подбиралась `llama-fit-params` отдельно под каждый бэкенд.

| Модель | Бэкенд | Блоков на CPU | без MTP | с MTP |
|---|---|---|---|---|
| **`ggml-org` Q4_0** | **ROCm** | **0** | 75 / 75 / 74 с | **66 / 65 / 65 с** |
| `ggml-org` Q4_0 | Vulkan | 3 | 87 / 105 / 107 с | 89 с |
| HauhauCS Q4_K_M | Vulkan | 6 | 139 с | 118 с |
| HauhauCS Q4_K_M | ROCm | 5 | 149 с | 112 с |

Строки с несколькими числами — повторные измерения.

**Ключевое отличие бэкендов здесь не в скорости арифметики, а в доступной памяти.** `--list-devices` показывает `ROCm0: 16230 MiB free` против `Vulkan0: 15148 MiB free`. Этого гигабайта хватает, чтобы 14.6-гигабайтная модель уместилась под ROCm **целиком**, и офлоад на CPU исчез. На большой модели запаса не хватает, офлоад нужен обоим, и преимущество ROCm пропадает.

**Воспроизводимость важнее средних.** Конфигурация без офлоада даёт разброс ±1 с. Конфигурация с офлоадом на той же машине плавает на 20% (87 → 105 → 107 с при идентичных аргументах). Причина: с `--load-mode none` веса читаются в RAM целиком, а вынесенные эксперты живут в host-памяти; при 31 ГБ RAM и 32 ГБ моделей на диске часть страниц уходит в swap (`pswpout` растёт), и каждый токен, которому нужен вынесенный эксперт, идёт через диск. Скорость начинает зависеть от того, что ещё успело осесть в памяти.

Это отдельно бьёт по ночному полному переводу из `04-translation-pipeline.md` — длинному фоновому прогону, где непредсказуемость хуже, чем несколько процентов скорости.

**Правило выбора:** прогнать `llama-fit-params` под оба бэкенда. Если под одним офлоад обнуляется, а под другим нет — брать первый. Если офлоад нужен обоим, разница между бэкендами на нашем замере оказалась в пределах систематики, так что выбирать можно по любому другому соображению.

**Осторожно с методикой.** Первая версия этого замера прогнала 8 конфигураций подряд по одному разу и получила порядок-зависимую систематику: каждая следующая загрузка модели ухудшала состояние памяти, так что ранние конфигурации выглядели быстрее поздних. Различия меньше 20% в такой схеме неразличимы. Строки без повторов в таблице выше сохранены как есть и интерпретации не подлежат.

### Ловушка с выбором устройства
`-dev` обязателен, но не из-за lavapipe: llama.cpp сама отфильтровывает софтверные Vulkan-устройства. Причина в другом — при сборке с обоими бэкендами `--list-devices` показывает **одну и ту же карту дважды**:
```
ROCm0:   AMD Radeon RX 9070 XT (16304 MiB, 16230 MiB free)
Vulkan0: AMD Radeon RX 9070 XT (RADV GFX1201) (16304 MiB, 15148 MiB free)
```
Без `-dev` llama.cpp разложит модель по «двум» устройствам, которые физически один GPU, и выделит память дважды. Всегда прибиваем: `-dev Vulkan0` или `-dev ROCm0`.

Проверено на этой машине: RADV на gfx1201 отдаёт только `VK_KHR_cooperative_matrix` (coopmat1); `VK_NV_cooperative_matrix2` есть исключительно у lavapipe. Оптимизации llama.cpp, идущие по пути coopmat2, нашу карту не затрагивают.

## Запуск llama-server (deploy/)

### Подбор раскладки
Не подбирать `--n-cpu-moe` вручную — есть `llama-fit-params`, который считает раскладку под доступную память:
```
llama-fit-params -m models/<model>.gguf -dev ROCm0 -c 16384 -ctk q8_0 -ctv q8_0 -fa on -t 8
```
Он печатает готовую строку аргументов, и это точнее `--n-cpu-moe N`, потому что выносит конкретные тензоры, а не «первые N слоёв». Прогонять под **оба** бэкенда: они видят разный объём свободной VRAM, и раскладка выходит разной.

Загрузчик при `-ot ...=CPU` предупреждает: `tensor overrides to CPU are used with mmap enabled - consider using --load-mode none for better performance`. Добавляем `--load-mode none`.

### Перевод (целевая конфигурация)
```
llama-server \
  -m models/ggml-org/gemma-4-26B-A4B-it-GGUF/gemma-4-26B-A4B-it-Q4_0.gguf \
  -md models/ggml-org/gemma-4-26B-A4B-it-GGUF/mtp-gemma-4-26B-A4B-it-Q4_0.gguf \
  --spec-type draft-mtp --spec-draft-n-max 2 \
  -dev ROCm0 -c 16384 -ngl 99 \
  -ctk q8_0 -ctv q8_0 -fa on -t 8 -np 1 --load-mode none \
  --metrics --host 127.0.0.1 --port 8080
```
- `-ot` не нужен: под ROCm модель влезает в VRAM целиком (14.34 ГБ, с MTP 14.71 ГБ сверх рабочего стола).
- `-t 8` по числу физических ядер, не 16: SMT на memory-bound нагрузке не помогает.
- 65 с на книгу из 92 абзацев, разброс ±1 с.

## MTP (спекулятивное декодирование)
Поддерживается для Gemma 4 и Qwen3.5/3.6. Флаги (сверено с `common/arg.cpp`):

- `-md, --model-draft, --spec-draft-model FNAME` — файл MTP-головы;
- `--spec-type draft-mtp` — тип спекулятивки (список через запятую);
- `--spec-draft-n-max N` / `--spec-draft-n-min N` — сколько токенов драфтить; начинать с 2, перебрать 1-6;
- `--spec-draft-cpu-moe`, `--spec-draft-n-cpu-moe` — офлоад драфтера, нам не нужен.

**Цена по памяти — 382 МБ** (замер: 14.34 ГБ без MTP против 14.71 ГБ с ним, сверх рабочего стола). Из них 241 МБ сам файл головы, остальное — её KV-кэш и вычислительные буферы. Расширять офлоад ради MTP не требуется.

### Что даёт MTP
Измерено с повторами на целевой конфигурации (`ggml-org` Q4_0, ROCm, офлоада нет): **75 / 75 / 74 с без MTP против 66 / 65 / 65 с с ним — 1.14x**. Полная таблица по бэкендам и моделям в разделе «Бэкенд» выше.

Заявленные Unsloth 1.4-2.2x и заявленные автором расцензуренной сборки ~35% на нашей нагрузке не достигаются. Причина не в MTP, а в форме нагрузки: префилл обрабатывает 24-37 тыс. токенов против ~5 тыс. сгенерированных, отношение **≈ 5 к 1**. Спекулятивка ускоряет только генерацию. **Увеличение доли кэша префикса даст больше, чем спекулятивка.**

Приём черновиков стабильно **48-49%** во всех замеренных сочетаниях модели и бэкенда: позиция 0 даёт 60-65%, позиция 1 — 36-43%. Падение вдвое ко второй позиции означает, что `--spec-draft-n-max 2` подобран верно и перебирать 1-6 незачем.

Приём не зависит от того, взята ли MTP-голова из той же сборки, что и модель: у расцензуренной сборки голова чужая (от немодифицированной модели), и приём у неё такой же. Значит ~50% — рабочая точка механизма, а не следствие рассогласования. Правила «брать голову только из своей сборки» не вводим, оснований нет.

### Вывод с MTP НЕ идентичен
Обещание «identical output» **не подтвердилось**. Замер: жадное декодирование (`temperature 0`, `top_k 1`), одна и та же раскладка, с MTP и без — совпало 5 из 12 абзацев, сходство 76%. Расхождения содержательные, а не пробельные: «Работаю я в известном…» против «Я работаю в известном…».

Алгоритм спекулятивки тут ни при чём: верификация действительно сохраняет распределение. Дело в арифметике — проверка N токенов за один проход меняет форму батча, а с ней порядок накопления чисел с плавающей точкой; логиты микроскопически плывут, и при близких вероятностях argmax выбирает другой токен.

То же самое объясняет более общий факт: **llama-server недетерминирован при сэмплировании даже с фиксированным seed** (совпало 8/12 абзацев, сходство 88%), потому что кэш префикса меняет разбивку на батчи. На жадном декодировании в пределах одной конфигурации сервер детерминирован — два прогона дали 12/12.

Практические следствия:
- `eval` и `compare` (`11-core-api-and-cli.md`) обязаны идти на `temperature 0` **и с выключенным MTP**, иначе шумовой пол в 12-24% расхождения перекроет измеряемый эффект;
- перевод в продакшене — не чистая функция от (модель, промпт, текст); `cache_key` из `03-storage.md` идентифицирует запись кэша, но не воспроизводимый результат.

## Режим рассуждений: выключать для перевода
Gemma 4 по умолчанию рассуждает перед ответом. На переводе это не «немного медленнее», а полный отказ: модель уходит в `message.reasoning_content`, `message.content` остаётся **пустым**, ответ упирается в `max_tokens` с `finish_reason: length`. Замерено: 400 токенов рассуждений о том, какой род выбрать, и ноль текста перевода.

Управление:

| Способ | Где | Работает |
|---|---|---|
| `chat_template_kwargs: {"enable_thinking": false}` | тело запроса | **да** — то, что нужно нам |
| `--reasoning off` (`-rea`) | аргумент сервера | да, но глобально |
| `reasoning_budget` | тело запроса | нет, только аргумент сервера |

Ставим **в каждом запросе** через `chat_template_kwargs`, потому что режим нужен разный: перевод абзаца — без рассуждений, компактификация контекста — возможно с ними (задача реже и тяжелее, стоит замерить обе ветки).

## Метрики
Сервер с `--metrics` отдаёт Prometheus-совместимый `GET /metrics`. Снимаем:

- `llamacpp:spec_decode_num_accepted_tokens_total` — принятые черновые токены;
- `llamacpp:spec_decode_num_accepted_tokens_per_pos_total` (метка `position="N"`) — на какой позиции черновик разваливается; заодно подсказывает оптимальный `--spec-draft-n-max`;
- ток/с и размер очереди — из `usage` ответов и из `/slots`.

`GET /props` даёт имя модели и настройки генерации по умолчанию, `GET /slots` — состояние слотов.
